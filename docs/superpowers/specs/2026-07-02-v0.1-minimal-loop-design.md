# LexiRoot v0.1 Minimal Loop — Design

Status: Approved
Date: 2026-07-02

## Context

LexiRoot's README describes a large end-state architecture: 9+ crates, a
build-time data pipeline sourced from Wiktionary/MorphoLex/Etymonline,
mobile and WebAssembly bindings, and a relationship graph. The project has
not been started yet. The README's own early review flags two blockers
that apply to the full vision — unresolved data licensing for the named
sources, and no validated real use case — and recommends proving a minimal
`core + cli` loop before splitting into the full crate set.

This spec scopes the *first* implementation pass: a small, legally clean,
end-to-end slice that proves the pipeline → database → analyzer → CLI loop
works, matching the README's own v0.1 milestone (word/prefix/suffix/root
database, morphology parser, SQLite export).

## Goals

- Prove the full loop: raw source data → normalized SQLite → Rust API →
  CLI output, with zero data-licensing risk.
- Implement `analyze()`, `root()`, and `family()` against real (if
  limited) data, matching the shapes shown in the README examples.
- Establish the `Provenance` (source, confidence, evidence) pattern from
  day one, since it's central to the "Explainable" design goal.

## Non-goals (explicit scope cuts for this pass)

- Etymology tracing (`etymology()`) — needs Wiktionary/etymwn data, which
  is CC BY-SA (share-alike) and deferred to a later pass.
- `graph` crate / generic relationship traversal — no graph algorithms are
  needed to serve `analyze`/`root`/`family` at this scale; building it now
  would be speculative.
- `search` crate, `ffi`, `wasm` — later roadmap milestones (v0.2+).
- `pipeline/validator` — both v0.1 sources are single-origin and MIT
  licensed; there's no cross-source conflict to resolve yet.
- Full English lexicon coverage. `root()`/`family()` "related words" are
  limited to whatever the source datasets list as example words for a
  given morpheme — this is a real coverage limit of this pass, not a bug.

## Data sources

Both MIT-licensed, chosen specifically to avoid the licensing risk the
README flags for Wiktionary/MorphoLex/Etymonline:

- [colingoldberg/morphemes](https://github.com/colingoldberg/morphemes) —
  prefixes/roots/suffixes grouped by shared meaning, with example words.
- [WithEnglishWeCan/generated-english-roots-list](https://github.com/WithEnglishWeCan/generated-english-roots-list) —
  roots, meanings, and example words.

MorphoLex-en was evaluated and rejected for this pass: it's CC
BY-NC-SA 4.0 (NonCommercial), which conflicts with the README's stated
goal of embedding LexiRoot in commercial mobile/desktop apps. Wiktionary
derivatives (wiktextract/kaikki.org, Etymological Wordnet) were evaluated
and deferred, not rejected: both are CC BY-SA, which allows commercial use
but requires attribution and share-alike handling on the distributed data.
That's real but manageable work, better done as its own pass once the
pipeline shape is proven.

Both source repos are vendored into `data/raw/<source-name>/` with their
original LICENSE files preserved. A `docs/DATA_SOURCES.md` records, per
source: upstream URL, license, and the pinned commit hash used — this
supports the README's "Immutable Releases" reproducibility goal (same
input → byte-identical release SQLite).

## Core domain model (`core` crate)

```rust
struct Morpheme {
    id: MorphemeId,
    form: String,           // e.g. "spect", "trans", "ation"
    kind: MorphemeKind,      // Prefix | Root | Suffix
    meanings: Vec<String>,
    provenance: Provenance,
}

struct WordDecomposition {
    word: String,
    segments: Vec<MorphemeRef>,  // ordered prefix(es)/root/suffix(es)
    provenance: Provenance,
}

struct Provenance {
    source: SourceId,       // enum identifying which dataset/pass produced this
    confidence: f32,         // 0.0-1.0
    evidence: String,        // human-readable explanation
}
```

No generic `Relationship`/graph struct is introduced this pass. The
README models it as a first-class part of the schema long-term, but
nothing in this slice needs graph traversal — `family()` is served
directly by `WordDecomposition` lookups grouped by shared `Morpheme`.
Adding the `graph` crate's own types when that crate is actually built
(v0.2) avoids carrying an unused abstraction now.

## Analyzer (`analyzer` crate) — hybrid segmentation

The source datasets are affix/root lists with example words, not a
pre-segmented corpus (that was MorphoLex-en's role, which is excluded).
So `analyze(word)` uses a two-tier strategy:

1. **Lookup**: if `word` matches a `WordDecomposition` built from a
   source-listed example, return it directly. `Provenance::SourceListed`,
   high confidence (e.g. 0.95).
2. **Algorithmic fallback**: greedy longest-match — strip the longest
   known prefix from the front and longest known suffix from the back
   (using a prefix/suffix trie built from the `Morpheme` table), then
   check the remainder against the root list for an exact match.
   `Provenance::Inferred`, lower confidence (e.g. 0.5), with `evidence`
   describing which affixes matched and what was stripped.
3. No match at either tier → `analyze` returns `None`.

This directly implements the README's "Explainable" goal: every result
carries a confidence score and evidence, and source-backed results are
visibly distinguished from inferred ones.

## `root()` / `family()`

- `root(text)` looks up a `Morpheme` by exact form and returns its
  meanings plus related words — words with a `WordDecomposition` segment
  referencing that morpheme. No etymology/origin field this pass (that
  needs the deferred Wiktionary data).
- `family(text)` groups `WordDecomposition` rows by shared root morpheme.

Both are limited to whatever words the source datasets happen to list as
examples — there is no dictionary of arbitrary English words to check
against yet.

## Pipeline

- `pipeline/importer`: parses the two source files' native formats,
  normalizes into `core` types, writes to `data/processed.sqlite` with
  per-record `Provenance` (`SourceId::ColinGoldbergMorphemes` /
  `SourceId::WithEnglishWeCanRoots`).
- `pipeline/exporter`: reads `processed.sqlite`, writes a deterministic
  `data/release/lexiroot-v0.1.sqlite` (stable sort order on export, so
  identical input always produces a byte-identical release file).

## CLI (`cli` crate)

- `lexiroot analyze <word>`
- `lexiroot root <text>`
- `lexiroot family <text>`

Opens the release SQLite, calls into `analyzer`, pretty-prints in the
format shown in the README examples.

## Testing strategy

- `core`: unit tests for schema construction/(de)serialization and
  `Provenance` invariants (confidence bounds, etc).
- `pipeline/importer`: fixture-file tests using a small hand-picked slice
  of real source data, asserting expected normalized rows.
- `analyzer`: one test per path — source-listed lookup, algorithmic
  fallback (a word not listed verbatim but composed of known affixes),
  and a not-found case.
- `cli`: one smoke test running each subcommand against a tiny fixture
  release DB.

## Open items for a future pass (not blocking this one)

- Etymology data source and `etymology()` (needs CC BY-SA attribution
  handling).
- `graph`/`search` crates once traversal/indexing needs actually exist.
- Cross-source validation once a second/third data source is added for
  the same morphemes (this is what `pipeline/validator` is for).
